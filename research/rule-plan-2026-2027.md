# ShipProof — Rule engineering and 5,000-rule expansion plan

วันที่: 2026-09-22 · สถานะ: proposed · Baseline `dd589b5` · ใช้ร่วมกับ [long-term plan](long-term-plan-2026-2027.md)

## 1. นิยามคำว่า “ครบ”

| หน่วย | ความหมาย | Baseline / เป้าหมาย |
| --- | --- | --- |
| Executable rule | Stable SP ID ที่ registry โหลดและ detector ทำงานจริง | ปัจจุบัน 640; เป้าหมายระยะยาว 5,000 unique active rules |
| Semantic family | Source → sink/unsafe state → sanitizer/context → remediation เดียวกัน | ใช้จัดกลุ่มและตรวจซ้ำ; หลาย CWE อาจเป็น family เดียว |
| Syntax variant | อีก spelling/API form ของ invariant เดิม | ขยายกฎเดิมเมื่อ proof/remediation เหมือนกัน |
| Test scenario | Input พร้อม expected findings/silence/omission และ rationale | เป้าหมาย corpus 5,000 distinct scenarios ใน 90 วัน; ไม่รวมเป็น rule count |
| Research candidate | คำถามที่มี source และยังต้องพิสูจน์ detectability | 7,800 records รวม language 5,000; ไม่รับประกันว่าทุก record ควรเป็น rule |
| External result | Finding จาก analyzer อื่นพร้อม original ID/tool identity | นับแยกจาก native ShipProof rules |

ช่องว่างถึง 5,000 executable คือ 4,360 ณ baseline หาก unique validated additions เฉลี่ย 10/25/50 ต่อสัปดาห์ จะใช้ประมาณ 436/175/88 สัปดาห์ตามลำดับ ก่อนหัก rules ที่ retire. นี่เป็น arithmetic planning ไม่ใช่ throughput ที่พิสูจน์แล้ว ใช้ 4 cohorts แรกวัด review capacity แล้วประมาณใหม่

ห้ามเติมกฎด้วย cross-product ของ language × CWE, aliases หรือ CVE versions เพื่อให้ครบจำนวน ถ้า candidate เหมาะกับ compiler/runtime/policy ให้ route ตามนั้นและนับ disposition อย่างเปิดเผย

## 2. แก้ promotion debt ก่อนขยาย

เริ่มด้วย LT-01–LT-08 ใน long-term plan โดยเฉพาะ SP104, SP668, SP669/SP670 และ eligibility ของ SP666–SP670. หลักฐานใหม่จาก probe แสดงว่า `blocking_eligible: false` ใน test manifest ไม่ได้ทำให้ runtime เป็น advisory: SP669 ยัง block ได้เมื่อเลือก medium/L0

แก้ระดับ semantics ก่อนเขียน tests เพิ่ม: การคาดหวังว่า safe configuration ต้องถูกแจ้ง จะสร้าง false-positive contract แม้ทุก test ผ่าน

ตัวอย่างที่ต้องอยู่ใน corpus ตั้งต้น:

- Dart custom trust store: `withTrustedRoots: false` + certificate ที่อนุญาต → ไม่อ้าง TLS bypass; callback ที่ยอมรับทุก certificate เป็นคนละ condition
- C# `DtdProcessing.Parse` + null/throwing resolver → แยก DTD policy/expansion จาก external entity access; ตรวจ framework/runtime version ของ XmlSecureResolver
- C `syslog(priority, format, ...)` → source ต้องอยู่ format position; `%s` กับ argv เป็น data ต้องเงียบ
- `LocalRedirect`, validated return URL, safe upload basename, escaped HTML, parameterized SQL → ต้องเป็น semantic negative ของกฎที่เกี่ยวข้อง
- `prefs` เป็น custom object และ `securePrefs` → ชื่อตัวแปรไม่พิสูจน์ว่า receiver เป็น SharedPreferences; ต้องมี binding หรือรายงาน uncertainty ชัดเจน

## 3. Lifecycle ที่ runtime และ docs ต้องใช้ร่วมกัน

`proposed → source-reviewed → fixture-ready → shadow → advisory → gate-eligible`

ทุกขั้นไป `rejected`, `merged`, `deprecated` ได้โดยเก็บเหตุผล/ID เดิม. Regression ส่งกลับ shadow/advisory พร้อม rule revision; ห้ามหายจาก inventory เงียบ ๆ

| ขั้น | Evidence ที่ต้องมี | Runtime effect |
| --- | --- | --- |
| Proposed | User failure mode, ecosystem/version, source lead, initial overlap | ไม่มี |
| Source-reviewed | Owning docs + CWE/control; exact semantics และ safe behavior; license provenance | ไม่มี |
| Fixture-ready | ≥3 positive, ≥5 realistic negative, ≥2 adversarial; walker test; bounds; deterministic identity | Test/shadow harness เท่านั้น |
| Shadow | Pinned representative corpus; labels; TP/FP/FN/TN; duplicate และ runtime delta | Explicit opt-in; ไม่เปลี่ยน production verdict |
| Advisory | Review ผ่าน, limitations/remediation ชัด, source/runtime metadata พร้อม | แสดงผลโดยไม่ block แม้ผู้ใช้เลือก L0/low |
| Gate-eligible | Representative measurements ผ่าน cohort policy; reviewer sign-off | เข้า severity/proof gate ตาม effective policy |

Severity บอก impact, confidence บอกความมั่นใจใน matched condition, proof บอกหลักฐาน, lifecycle บอกความพร้อม และ eligibility บอกสิทธิ์เปลี่ยน verdict. ห้ามใช้ medium severity แทน advisory flag

## 4. Rule record ที่เสนอ

ใช้ candidate IDs แบบ `DART-xxx`, `DOTNET-xxx`, `C-xxx` สำหรับงานใหม่; SP IDs เดิมใน research ต้องเก็บ mapping ไม่ renumber. SP runtime ID จองตอน review อนุมัติ semantic family

```yaml
candidate_id: DART-011
rule_id: null
rule_revision: 1
ecosystem: dart
applicable_versions: pending-source-review
semantic_key: dart.httpclient.tls.unconditional-accept
lifecycle: proposed
gate_eligible: false
proof_claim: Direct unconditional certificate acceptance callback
source_binding: dart:io HttpClient or verified alias
unsafe_state: callback always returns true
safe_cases: [custom-trust-store, conditional-pinning]
engine: bounded-structural
sources: [] # Fill exact URL, version/date, claim, license before promotion.
overlap_review: []
fixtures: {positive: [], negative: [], adversarial: []}
walker_evidence: null
shadow_metrics: null
runtime_delta: null
reviewer: null
decision: pending
```

เพิ่ม field source/sink/argument index, sanitizers, scope, failure behavior, CWE/control, remediation และ limitation ตาม rule type; schema validator ต้อง reject unknown/missing fields ที่มีผลต่อ verdict. Registry count derive จาก loaded metadata; docs release derive จาก immutable release snapshot

## 5. Priority และ review budget

ให้ reviewer ให้คะแนน 1–5: `3×user impact + 3×local observability + 2×field evidence + reuse benefit − 3×ambiguity − implementation cost − maintenance cost`. คะแนนเป็น prioritization heuristic ไม่ใช่ severity หรือ precision

เลือก repair-existing ก่อน new ID เมื่อ root cause เดิม. สำหรับ 4 cohorts แรก แบ่ง effort ประมาณ 50% Dart, 30% C#/.NET, 20% C/C++; ถ้าส่วนใดติด engine prerequisite ให้ทำ corpus/source review ที่มีประโยชน์ก่อน

WIP: 10–25 reviewed proposals, 3–10 implementations ต่อ integration batch, reviewer queue ≤2 batches. วัด accepted rules/reviewer-day, false-positive regressions, time-to-label และ runtime cost; AI ช่วยร่าง/จัดข้อมูลได้ แต่ AI agreement ไม่ใช่ independent ground truth

## 7. Evaluation ที่วัดความแม่นยำได้

**Unit ที่นับ:** positive sink site และ safe code site ที่มี label; แยก file/repository-level metrics. Unknown ไม่อยู่ใน TP/FP/TN/FN แต่ต้องรายงานจำนวนและเหตุผล; missed known vulnerable sites นับ FN แม้ scanner ไม่ emit อะไร

ก่อน advisory: ≥3 positive, ≥5 realistic negative, ≥2 adversarial ต่อ rule พร้อม real walker, multiline, comments/strings, import aliases, shadowed names, wrong suffix, generated/test scope, malformed/oversized input, line anchors และ duplicate interactions. Test family เพิ่ม cases ตาม ambiguity ไม่จำกัดอยู่ที่ขั้นต่ำสิบตัว

ก่อน gate-eligible (proposed policy):

- ≥3 unrelated representative repositories ต่อ semantic family พร้อม pinned revision/license; application และ library context ตาม applicability
- ≥100 manually reviewed emitted sites ต่อ family และ ≥100 reviewed safe opportunities; sample อย่างมีเหตุผล ไม่เลือกเฉพาะผลที่ถูกง่าย ๆ
- มี known vulnerable cases ครอบคลุม supported flow และอย่างน้อย 20 sites ต่อ family สำหรับ recall; synthetic/curated/field แยก metric
- Observed precision ≥98%, one-sided 95% lower confidence bound ≥95%, recall ≥90% ภายใน declared scope; จำนวน sample/interval method ต้องเผยแพร่
- confirmed high/critical gate false positives = 0 ใน release corpus; discovery of FP ต้องหยุด gate promotion เพื่อแก้ แต่ zero observed FP ไม่เท่ากับ FP rate ศูนย์ทั่วไป
- ไม่มี unsupported scope ถูกนับเป็น “scanned clean”; phase timeout และ parser failure รักษา exit/completeness semantics

Rule ใหม่ sample ยังน้อยให้คง advisory/shadow. Family metric ใช้ร่วมได้เฉพาะ implementation/source/sink/sanitizer เดียวกันที่อธิบายได้ ต้องรายงาน rule-specific results ด้วย ห้ามซ่อน rule ที่ผิดด้วย average ของ rule ที่ดี

แบ่ง development / holdout repositories ตาม project และ commit history; อย่าเอา variants ของต้นฉบับเดียวกันใส่สองฝั่ง. Labeler เห็น source และ invariant ก่อนดู detector result เมื่อทำได้; disputed labels บันทึก rationale และใช้ผู้ตรวจอีกคน ถ้าไม่มี independent reviewer ให้รายงาน self-review

## 8. 90-day corpus target: 5,000 scenarios

| กลุ่ม | Positive | Realistic negative | Adversarial | Total |
| --- | ---: | ---: | ---: | ---: |
| Dart / Flutter | 600 | 1,000 | 400 | 2,000 |
| C# / .NET | 540 | 900 | 360 | 1,800 |
| C / C++ | 360 | 600 | 240 | 1,200 |
| Total | 1,500 | 2,500 | 1,000 | 5,000 |

นี่คือ coverage target ของ scenarios โดย independent semantic situations; whitespace/identifier mutation ใช้ robustness suite และนับแยก. ถ้ายัง review ไม่ครบให้รายงาน partial; ไม่สร้าง safe strings หรือ duplicates เพื่อครบ quota

โครงสร้างที่เสนอ: `tests/rule-cases/<ecosystem>/<family>/` + manifest identity + expected results + provenance; generator สร้าง syntax variations จาก case ที่ label แล้วได้ แต่ไม่สร้าง correctness labels เอง. กฎเดิม 423 high/critical ที่ขาด realistic negatives ใช้ corpus นี้ช่วยลด debt โดยไม่สรุปว่าทุกตัวผิด

## 9. Batch workflow และ acceptance

1. เลือก failure mode และ exact API semantics; ตรวจ overlap ด้วย semantic key, matching output, sink และ remediation
2. เขียน official-safe negative และ expected unsafe case ก่อน matcher; validate sample syntax ด้วย local runtime/compiler ใน sandbox เมื่อมี; ไม่ติดตั้ง tool ผ่าน default scan
3. เลือก engine ตาม evidence; structural/data-flow prerequisite ที่ไม่พร้อมให้ park พร้อมงาน prerequisite
4. Run matcher + real walker + CLI/JSON/SARIF parity; test advisory eligibility ผ่าน `low/medium/high` และ proof `L0/L1/L2`
5. Run pinned shadow corpus, human labeling, duplication checks, performance A/B; document unsupported variants
6. Integrate 3–10 approved detectors/extensions; regenerate applicable contracts/docs; full check + self-scan + package gate + current-commit CI
7. บันทึก rule revision, verdict change, review ownership, rollback target และผลจริง; keep historical release notes immutable

พิจารณาแยกต่อ batch: accepted new IDs, existing extensions, merged duplicates, rejected proposals, parked engine work, new scenarios, measured precision/recall และ runtime delta. การแก้ metadata/docs อย่างเดียวไม่นับ executable addition
